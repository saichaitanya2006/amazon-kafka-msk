STEP 1

Amazon MSK Multi-AZ Cluster Overview & Fault Tolerance

🎙️ SPOKEN TELEPROMPTER SCRIPT (Read Aloud):

"Good morning everyone. Today, I am demonstrating our enterprise event streaming platform built on Amazon Managed Streaming for Apache Kafka (Amazon MSK). As you can see on the overview dashboard, our cluster is running Kafka version 3.6.0 in KRaft consensus mode. We have deployed three dedicated broker nodes distributed across three separate AWS Availability Zones in us-east-1: Zones 1A, 1B, and 1C. This guarantees multi-AZ fault tolerance with zero single points of failure. Even if an entire AWS data center goes offline, our cluster retains 100% in-sync replicas with zero under-replicated partitions. The real-time charts below stream live CloudWatch velocity metrics with latency under 4 milliseconds."

🧠 UNDER-THE-HOOD TECHNICAL DEFENSE:

KRaft Mode: Eliminates legacy external ZooKeeper dependencies. Partition leader elections take < 90ms. Each broker uses AWS GP3 EBS volumes with dedicated IOPS and multi-AZ synchronous replication (min.insync.replicas=2).

Reviewer Question: "Why Amazon MSK instead of self-hosting Kafka on EC2?"
Your Answer: "Self-hosting requires manual OS patching, ZooKeeper maintenance, and custom rebalancing scripts. Amazon MSK automates broker healing, storage auto-expansion, rolling upgrades, and integrates natively with AWS IAM and KMS encryption."
STEP 2

Real-Time Event Producer Studio & Partition Routing

🎙️ SPOKEN TELEPROMPTER SCRIPT (Read Aloud):

"Next, we demonstrate the producer layer in our Event Producer Studio. Upstream microservices, IoT devices, or payment gateways publish records to Kafka topics. Here, we select the IoT Telemetry Heartbeat template stamped with sensor diagnostics. Notice the Partition Key: Kafka hashes this key using the Murmur2 algorithm to guarantee strict FIFO ordering within the same partition. Upon clicking 'Publish to MSK', our backend ingests the payload, assigns it to Broker 1, and responds with an acknowledgment in just 2.15 milliseconds, assigning offset #30412."

🧠 UNDER-THE-HOOD TECHNICAL DEFENSE:

Partitioning: hash(key) % partitions ensures records for the same device or customer are serialized sequentially in one partition. acks=all guarantees the leader broker commits the message to follower replicas before responding.

Reviewer Question: "How do you handle invalid schemas?"
Your Answer: "Our client verifies JSON syntax and payload size prior to dispatch. In production, this connects to AWS Glue Schema Registry to enforce strict backward/forward schema compatibility checks."
STEP 3

High-Throughput Concurrency & Burst Ingestion

🎙️ SPOKEN TELEPROMPTER SCRIPT (Read Aloud):

"In Step 3, we test cluster scalability by triggering a Burst of 25 concurrent events. In the ACKs panel, notice how partition assignments are immediately parallelized across Partition 0, 1, and 2 across all three brokers. Because Kafka topics are partitioned append-only logs, write operations do not block each other, demonstrating linear horizontal scalability under flash-traffic spikes."

🧠 UNDER-THE-HOOD TECHNICAL DEFENSE:

Throughput Parallelization: Each partition has its own dedicated write log, eliminating single-disk bottlenecks. Micro-batching (linger.ms=5) ensures optimal network packet utilization.

STEP 4

Live Stream Consumer Inspector & Record Anatomy

🎙️ SPOKEN TELEPROMPTER SCRIPT (Read Aloud):

"Having published events, we now inspect the downstream consumer experience in the Live Stream Inspector. Whenever an event is ingested, it is broadcast to connected consumers over persistent WebSockets. Clicking 'Inspect' reveals the internal anatomy of a Kafka record: the immutable 64-bit Offset, the Broker Leader, Distributed Tracing Headers, and the decoded JSON payload."

🧠 UNDER-THE-HOOD TECHNICAL DEFENSE:

Offset Semantics: Offsets are sequential integers. Unlike traditional message queues (e.g. SQS), consuming a message does not delete it; independent consumers read at their own pace or replay history arbitrarily.

STEP 5

Managed Kafka Topic Provisioning & Partition Cardinality

🎙️ SPOKEN TELEPROMPTER SCRIPT (Read Aloud):

"Step 5 demonstrates cluster administration. Topics are the foundational channels in Kafka. As shown on screen, we dynamically provisioned analytics.fraud.stream.v1 with 6 partitions to support high consumer concurrency, a replication factor of 3 for multi-AZ safety, and 7-day retention. The topic is validated and immediately available across the cluster."

🧠 UNDER-THE-HOOD TECHNICAL DEFENSE:

Partition Count: Partition counts dictate maximum consumer parallel concurrency. Partitions can be expanded at runtime but cannot be reduced without recreating the topic.

STEP 6

Consumer Groups & Offset Lag Monitoring

🎙️ SPOKEN TELEPROMPTER SCRIPT (Read Aloud):

"Step 6 addresses the health of downstream data consumers: Consumer Group Lag. A consumer group allows multiple worker containers to cooperatively consume topic partitions. 'Lag' represents the delta between the producer's latest offset and the consumer's committed offset. As verified by our green progress indicators, lag remains close to zero, proving downstream microservices process transactions in real time."

🧠 UNDER-THE-HOOD TECHNICAL DEFENSE:

CooperativeStickyAssignor: Eliminates legacy 'stop-the-world' consumer rebalancing. Only affected partitions migrate when new consumer workers join or leave.

Security & Resilience: Strict VPC subnet isolation, TLS 1.3 encryption, and AWS IAM authentication. Cross-region disaster recovery supported via Amazon MSK Replicator."
